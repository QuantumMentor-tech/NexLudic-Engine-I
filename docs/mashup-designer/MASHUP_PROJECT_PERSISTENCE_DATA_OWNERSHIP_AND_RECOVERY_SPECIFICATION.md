## 1. PURPOSE AND STORAGE PRINCIPLES

### 1.1 Purpose
This specification establishes the logical persistence model, filesystem storage hierarchy, data ownership classification, atomic commit mechanisms, and corruption recovery procedures governing **Mashup Projects** (`MashupProject`) within NexLudic Engine.

In accordance with `DEC-009` and Phase 2 storage architecture (`NLE-ARC-DOC-004`), project data is maintained under an isolated, local filesystem hierarchy on Volume D. This document specifies:
1. The exact directory layout and file structures on Volume D.
2. The classification of authoritative vs. referenced vs. derived data.
3. Atomic write operations preventing partial file corruption.
4. Backup, revision snapshotting, and archive import/export policies.

---

## 2. VOLUME D FILESYSTEM HIERARCHY (`DEC-009`, `ADR-0009`)

Every Mashup Project is allocated a self-contained, isolated directory tree anchored strictly to Volume D:

```
D:\NexLudic\
    └── Projects\
        └── <projectId>\                    <-- RFC 4122 UUIDv4 project folder
            ├── project.json                <-- Authoritative active project aggregate root
            ├── .draft.json                 <-- Ephemeral autosave draft (wiped on clean exit)
            ├── .lock                       <-- Inter-process file write mutex lock
            ├── revisions\                  <-- Immutable historical snapshots
            │   ├── rev_0001.json
            │   ├── rev_0002.json
            │   └── ...
            ├── .audit\                     <-- Immutable audit logs
            │   ├── revisions.audit.jsonl   <-- SHA-256 rolling chain audit log
            │   └── checkpoint.sha256
            └── plan\                       <-- Phase 6 Integration Planner outputs
                └── integration_plan.json   <-- Compiled mashup plan (Phase 6 Step 45+)
```

## 3. DATA OWNERSHIP AND CLASSIFICATION TAXONOMY

To eliminate data duplication and out-of-sync states, data within a project is strictly categorized:

| Data Category | Definition | Examples | Authoritative Source | Persistence Policy |
| :--- | :--- | :--- | :--- | :--- |
| **Project-Owned Inputs** | Data authored directly by the creator within the project scope. | Project name, description, objective, feature requirements, strategy choice. | `MashupProject` (`project.json`) | **Authoritative & Persisted** |
| **External References** | Pointers to authoritative data managed by other platform subsystems. | `canonical_game_id`, `edition_id`, `adapter_id`, `capability_id`. | Phase 4 Catalog, Phase 5 Registry | **Persisted as ID references only** |
| **Derived Outputs** | Computations generated by platform engines evaluating project inputs. | Compatibility reports, capability match scores, negotiated parameter maps. | Matching Engine, Evaluator | **Cacheable & Invalidation-Bound** |
| **Runtime Observations** | Real-time execution metrics captured while adapters are running. | Process PIDs, ping roundtrips, 60Hz frame latencies, hook states. | Core Supervisor (`CMP-08`) | **Ephemeral (Never in project.json)** |

> [!CAUTION]
> A Mashup Project MUST NOT clone or store duplicate copies of mutable catalog records or adapter manifests. It stores strictly the canonical identifier (e.g. `canonical_game_id`, `adapter_id`). If an adapter is updated, the project queries the registry for the latest state.

## 4. ATOMIC WRITES AND CORRUPTION MITIGATION

### 4.1 Write-to-Temp-and-Rename Protocol
To guarantee that system crashes or power losses during save operations cannot corrupt `project.json`:
1. The engine serializes the updated JSON payload to an ephemeral temporary file:  
   `D:\NexLudic\Projects\<projectId>\project.json.tmp.<uuid>`
2. The engine flushes all file buffers to disk via Win32 `FlushFileBuffers`.
3. The engine replaces the active file using the atomic Win32 `ReplaceFileW` API (or POSIX `rename` equivalent), guaranteeing an all-or-nothing disk commit.
4. Direct in-place writes to `project.json` are strictly prohibited.

### 4.2 Inter-Process File Concurrency Locks
- Writing to project files is guarded by an inter-process named mutex:  
  `Global\NexLudic_ProjectLock_<projectId>`
- Any secondary process attempting to modify the project while a save is in progress waits up to 3,000 ms before returning `ERR_PRJ_CONCURRENT_WRITE_LOCK`.

## 5. PROJECT ARCHIVING, EXPORT, AND PURGE LIFECYCLE

### 5.1 Project Export (`.nlproj`)
- A project can be exported as a standalone archive file (`.nlproj`).
- Format: Unencrypted, standard ZIP archive containing `project.json` and the `revisions/` directory.
- Sanitization: All absolute local paths are stripped and replaced with relative placeholders during export packaging.

### 5.2 Project Import Security Verification
When a user imports an external `.nlproj` archive:
1. **Path Traversal Scan:** Archive is scanned to ensure zero `..` sequences or drive letters exist.
2. **UUID Re-Keying:** If the imported `project_id` collides with an existing local project, the engine assigns a fresh UUIDv4 to avoid overwriting existing user data.
3. **Schema Validation:** The imported `project.json` is validated against `NLE-SCH-MPD-001`.

### 5.3 Two-Stage Purge Deletion
1. **Stage 1 (Soft Delete):** Lifecycle state transitions to `PROJECT_DELETED`. Project is hidden from workspace lists.
2. **Stage 2 (Physical Purge):** After explicit user confirmation (and a 7-day grace window), the physical directory `D:\NexLudic\Projects\<projectId>\` is deleted from disk.
