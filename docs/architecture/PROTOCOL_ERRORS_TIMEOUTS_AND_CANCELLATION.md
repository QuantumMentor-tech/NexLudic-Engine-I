## 1. Executive Summary & Resilience Principles

Inter-Process Communication between the NexLudic Engine Core Host and external game adapters operates across process boundaries that can experience unexpected termination, memory exhaustion, deadlock, unhandled native exceptions, and network/pipe failures. 

To prevent platform hangs, corrupted mod workspaces, and silent failures, NexLudic Engine establishes:
1. A **Universal 18-Category Error Taxonomy** providing structured diagnostics and retry semantics.
2. Strict **Timeouts and Deadline Budgets** across all operations.
3. A robust **Two-Phase Cooperative Cancellation Protocol** backed by forceful sandbox eviction.
4. An automated **Circuit Breaker & Retry Strategy** to isolate malfunctioning adapters.

## 2. Universal 18-Category Error Taxonomy

Every error returned within a message envelope or generated by the IPC transport layer MUST map directly into one of the 18 standardized error categories:

```
                                UMP ERROR CATEGORY TAXONOMY
                                             |
    +--------------------+-------------------+--------------------+--------------------+
    |                    |                   |                    |                    |
 1. TRANSPORT         2. PROTOCOL         3. SECURITY          4. PROCESS           5. TIMEOUT
 - CONNECTION_LOST    - MALFORMED_MSG     - UNAUTHORIZED       - SPAWN_FAILED       - HANDSHAKE_EXPIRED
 - BUFFER_OVERFLOW    - UNSUPPORTED_VER   - INVALID_SIGNATURE  - UNEXPECTED_TERM    - OPERATION_EXPIRED
                      - UNEXPECTED_TYPE                                             - HEARTBEAT_EXPIRED
    +--------------------+-------------------+--------------------+--------------------+
    |                    |                   |                    |                    |
 6. CAPABILITY        7. OPERATION        8. RESOURCE          9. VALIDATION
 - UNSUPPORTED        - CANCELLED         - EXHAUSTED          - SCHEMA_VIOLATION
 - PREREQ_FAILED      - FAILED_INTERNAL
```

### Detailed Taxonomy Specification Table:

| Error Category Code | Subsystem Domain | Description & Failure Trigger | Is Retryable? | Default Action |
| :--- | :--- | :--- | :--- | :--- |
| `TRANSPORT_CONNECTION_LOST` | IPC Transport | The underlying stdio pipe or named pipe connection was unexpectedly closed or broken. | Yes (after restart) | Mark worker dead; re-spawn worker if operation was idempotent. |
| `TRANSPORT_BUFFER_OVERFLOW` | IPC Transport | Incoming message exceeded the 16 MB Control Channel or 64 MB Data Channel buffer limit. | No | Terminate stream; drop connection; report memory violation. |
| `PROTOCOL_MALFORMED_MESSAGE`| Protocol Framing | The received payload failed basic JSON syntax parsing or binary Protobuf frame decoding. | No | Emit diagnostic log; discard frame; do not retry identical payload. |
| `PROTOCOL_UNSUPPORTED_VERSION`| Versioning | Core and worker have no overlapping supported `MAJOR` protocol versions. | No | Abort session initialization; report adapter incompatibility. |
| `PROTOCOL_UNEXPECTED_MESSAGE_TYPE`| State Machine | Received a message illegal in current state (e.g. `operation.invoke.progress` before `accepted`). | No | Reject message with protocol error; log state machine violation. |
| `SECURITY_UNAUTHORIZED_CALLER`| Security Policy | Caller lacks valid session auth token or attempted an administrative elevation operation. | No | Terminate connection immediately; log security security alert. |
| `SECURITY_INVALID_SIGNATURE`| Security Policy | Manifest cryptographic signature or HMAC token mismatch. | No | Reject adapter registration; flag potential tampering. |
| `PROCESS_SPAWN_FAILED` | Process Lifecycle| Operating system failed to execute worker binary (missing dependencies, invalid path, ACL).| No | Report OS exit error code to user UI; mark adapter disabled. |
| `PROCESS_UNEXPECTED_TERMINATION`| Process Lifecycle| Worker process died abruptly with non-zero exit code or OS fault while operations active. | Yes (Idempotent only)| Clean up staging locks; fail pending operations; notify supervisor. |
| `TIMEOUT_HANDSHAKE_EXPIRED` | Timeout Budget | Worker failed to return `session.handshake.response` within 10,000 ms of launch. | No | Force-terminate worker via Job Object; declare init failure. |
| `TIMEOUT_OPERATION_EXPIRED` | Timeout Budget | Operation exceeded its allotted `timeout_ms` or passed its `deadline_utc` cutoff. | No | Send cancel request; fail calling task with timeout error. |
| `TIMEOUT_HEARTBEAT_EXPIRED` | Timeout Budget | Worker missed three consecutive health pings (15,000 ms silence). | No | Declare worker unresponsive; force-terminate via Job Object. |
| `CAPABILITY_UNSUPPORTED` | Capability Model | Request invoked an operation or trait not declared in worker's capability manifest. | No | Fast-fail request; do not dispatch to worker. |
| `CAPABILITY_PREREQUISITE_FAILED`| Capability Model | Target game binary, modding tool, or required staging directory is missing or invalid. | No | Notify user to install missing prerequisite software. |
| `OPERATION_CANCELLED` | Operation Lifecycle| The operation was successfully aborted prior to completion via cooperative cancellation. | No | Clean up intermediate files; notify caller of cancellation. |
| `OPERATION_FAILED_INTERNAL`| Execution Domain| Unhandled internal exception occurred within the adapter worker during task execution. | Depends on payload| Propagate inner stack trace; evaluate adapter error details. |
| `RESOURCE_EXHAUSTED` | System Resource | Worker exceeded memory commit limit (2 GB Job Object cap) or disk space was exhausted. | No | Halt operation; suggest increasing system memory or clearing disk. |
| `VALIDATION_SCHEMA_VIOLATION`| Data Validation | Request or response payload properties failed schema validation constraints. | No | Reject invalid message; surface schema validation errors. |

## 3. Request / Response Semantics & Invariants

To avoid data corruption during mod generation and live mashup execution, UMP enforces the following execution invariants:

```
+-----------------------------------------------------------------------------------+
|                        INVOCATION SEMANTICS & INVARIANTS                          |
|                                                                                   |
|  1. AT-MOST-ONCE SEMANTICS FOR NON-IDEMPOTENT OPERATIONS:                         |
|     - Operations that mutate state or filesystem artifacts (e.g. inject files,    |
|       patch game binaries, write save files) MUST NOT be automatically retried on |
|       transport disconnection unless explicitly marked `is_idempotent: true`.    |
|                                                                                   |
|  2. AT-LEAST-ONCE SEMANTICS FOR IDEMPOTENT OPERATIONS:                            |
|     - Read-only queries (e.g. `capability.query`, `file.hash`, `adapter.status`)   |
|       may be safely retried up to 3 times with exponential backoff.               |
|                                                                                   |
|  3. DETERMINISTIC CORRELATION INVARIANT:                                          |
|     - Every response MUST mirror the caller's `message_id` into its               |
|       `correlation_id`. A response with an unknown or null `correlation_id` is    |
|       treated as an orphan frame and discarded with a warning.                    |
|                                                                                   |
|  4. STRICT TIMEOUT BUDGET ENFORCEMENT:                                            |
|     - The Core caller decrements remaining timeout budget across network hops.    |
|     - If `deadline_utc` is reached while in worker queue, worker MUST drop the    |
|       task immediately and return `TIMEOUT_OPERATION_EXPIRED`.                    |
+-----------------------------------------------------------------------------------+
```

## 4. Timeout Budgets & Lifecycle Deadlines

All time budgets are formally standardized across the engine:

```
+-----------------------------+---------------------+-------------------------------+
| Lifecycle Event / Task      | Default Timeout     | Hard Maximum / Eviction Bound |
+-----------------------------+---------------------+-------------------------------+
| Process Handshake           | 10,000 ms (10.0 s)  | 15,000 ms (Kill worker)       |
| Health Ping / Pong          | 2,500 ms (2.5 s)    | 15,000 ms (3 missed = Evict)  |
| Capability Discovery Query  | 5,000 ms (5.0 s)    | 10,000 ms                     |
| Short RPC Command (Inspect) | 5,000 ms (5.0 s)    | 15,000 ms                     |
| Mod Workspace Scaffolding   | 30,000 ms (30.0 s)  | 60,000 ms                     |
| Script / Asset Compilation  | 60,000 ms (60.0 s)  | 300,000 ms (5 minutes)        |
| Cooperative Cancellation    | 5,000 ms (5.0 s)    | 5,000 ms (Watchdog force kill)|
| Clean Shutdown Request      | 5,000 ms (5.0 s)    | 7,000 ms (Force Job terminate)|
+-----------------------------+---------------------+-------------------------------+
```

## 5. Two-Phase Cooperative Cancellation Protocol

When a user cancels a mod generation task, or when the Core supervisor detects an expired deadline, cancellation executes through a strictly sequenced two-phase protocol:

```
Core Supervisor                                             Adapter Worker
      |                                                           |
      | 1. operation.cancel.request                               |
      |    [operation_id: "op-101", reason: "User Abort"]         |
      | --------------------------------------------------------> |
      |                                                           | --+ (Worker signals
      |                                                           |   | CancellationToken;
      |                                                           |   | ceases child processes;
      |                                                           |   | rolls back staging edits)
      |                                                           | <-+
      | 2. operation.cancel.response                              |
      |    [operation_id: "op-101", status: "CANCELLED"]          |
      | <-------------------------------------------------------- |
      |                                                           |
      | (If no response within 5,000 ms Grace Period):            |
      | ========================================================= |
      | 3. SAFETY WATCHDOG FALLBACK:                              |
      |    Core invokes Win32 TerminateJobObject on sandbox.      |
      |    Worker process and all child mod tools are killed.     |
      | ========================================================= |
```

### State Transitions during Cancellation:
1. `RUNNING`: Operation actively executing.
2. `CANCELLING`: Core issued `operation.cancel.request`. Worker CancellationToken triggered.
3. `CANCELLED`: Worker successfully terminated operation, rolled back partial files, and returned `status: "CANCELLED"`.
4. `TERMINATED_BY_WATCHDOG`: Worker hung or refused to yield within 5,000 ms; Core forcefully killed process tree.

## 6. Circuit Breaker & Retry Policy

To prevent cascading failures when an adapter is unstable or repeatedly faulting:

```
           +---------+  Success Threshold (x3)  +--------------+
           |         | <----------------------- |              |
           | CLOSED  |                          |  HALF-OPEN   |
           | (Normal)| -----------------------> | (Canary Test)|
           +---------+   Failure Threshold (x3) +--------------+
                                                       ^
                                                       | Reset Timeout (30s)
                                                +--------------+
                                                |              |
                                                |     OPEN     |
                                                |  (Tripped)   |
                                                +--------------+
```

1. **Closed State (Normal):** All requests pass through to the adapter.
2. **Trip Condition:** If an adapter experiences **3 consecutive unexpected crashes or timeouts** within a 60-second window, the circuit trips to **Open**.
3. **Open State:** Core immediately fast-fails incoming requests with `PROCESS_UNEXPECTED_TERMINATION` or `RESOURCE_EXHAUSTED` without attempting to launch or invoke the worker.
4. **Half-Open State (Canary Probe):** After a **30-second cooldown period**, the circuit transitions to Half-Open. A single canary `health.ping` and `capability.query` is dispatched. If successful, the circuit resets to **Closed**; if it fails, the circuit returns to **Open** for a 120-second backoff penalty.
